OCR выполняет детерминированные инженерные операции (выбор файлов, разрешение
правил), а основной агент проводит само код-ревью, используя возможности
собственной LLM. На стороне OCR эндпоинт LLM не требуется.

## Когда использовать режим делегирования

Режим делегирования предназначен для AI-агентов программирования по подписке,
таких как Claude Code, Codex, Cursor, Open Code, Qoder и другие, где подписка
на LLM уже включена в основной агент. Вместо настройки отдельного эндпоинта
модели для OCR вы используете существующую квоту подписки основного агента для
проведения ревью.

Используйте режим делегирования, когда:

1. Ваш AI-агент программирования работает по подписке, и вы хотите использовать
   её квоту для код-ревью без дополнительного API-ключа или настройки модели.
2. От OCR требуется только инженерный каркас: фильтрация файлов, разрешение
   правил и логика исключений, а все рассуждения LLM выполняет основной агент.
3. Вы создаёте собственный агентный конвейер, которому нужны структурированные
   входные данные (список файлов и правила) для собственного этапа ревью.

## Предварительные требования

CLI `ocr` должен быть установлен:

```bash
which ocr || npm install -g @alibaba-group/open-code-review
```

Конфигурация LLM (`ocr config set …` или переменные окружения) не требуется:
в режиме делегирования OCR никогда не вызывает LLM на своей стороне.

## Установка навыка / команды

### Claude Code — команда

```bash
mkdir -p .claude/commands
curl -o .claude/commands/delegate-review.md \
  https://raw.githubusercontent.com/alibaba/open-code-review/main/plugins/open-code-review/claude-code/commands/delegate-review.md
```

### Любой агент — навык

```bash
npx skills add alibaba/open-code-review --skill open-code-review-delegate
```

Или скопируйте манифест вручную:

```bash
cp -R /path/to/open-code-review/skills/open-code-review-delegate ~/.claude/skills/
```

## Рабочий процесс

### Шаг 1. Предварительный просмотр — определить, что проверять

```bash
ocr delegate preview [--from <ref> [--to <ref>]] [--commit <hash>] [--scan] [--exclude <patterns>]
```

Вывод содержит:

- **режим** — workspace / range / commit / scan;
- **метаданные ссылок** — from, to, commit, merge\_base;
- **список проверяемых файлов** — пути, статусы, добавления/удаления;
- **исключённые файлы** — с причиной исключения.

Распространённые варианты вызова:

| Сценарий | Команда |
|----------|---------|
| Изменения рабочей области | `ocr delegate preview` |
| Сравнение веток | `ocr delegate preview --from main --to feature` |
| Текущая ветка относительно main | `ocr delegate preview --from main` |
| Один коммит | `ocr delegate preview -c abc123` |
| Весь репозиторий | `ocr delegate preview --scan` |

Режим scan перечисляет всё рабочее дерево по стандартным правилам сканирования — `.gitignore`, include/exclude-правила, список разрешённых расширений и секретные пути — поэтому базовая точка diff не нужна. Его нельзя комбинировать с `--from`, `--to` или `--commit`.

### Шаг 2. Получить правила для файлов

```bash
ocr delegate rule [--from <ref> [--to <ref>]] [--commit <hash>] <path1> <path2> ...
```

Передайте проверяемые пути из шага 1. Вывод группируется по содержимому правил:
файлы с одинаковым правилом находятся в одной группе, что позволяет избежать
повторений.

### Шаг 3. Получить diff

Выберите команду diff по режиму и ссылкам из шага 1. При каждом вызове Git во время ревью используйте `git --no-pager`.

Следующие команды diff отключают внешние diff-программы, преобразование текста и цветной вывод, чтобы получить патчи в виде обычного текста.

**Режим диапазона** (предоставлен merge\_base):
```bash
git --no-pager diff --no-ext-diff --no-textconv --no-color <merge_base>..<to> -- "<path>"
```

**Режим коммита**:
```bash
git --no-pager show --no-ext-diff --no-textconv --no-color <commit> -- "<path>"
```

**Режим рабочей области**:
```bash
git --no-pager diff --no-ext-diff --no-textconv --no-color HEAD -- "<path>"        # tracked files
cat "<path>"                     # new untracked files
```

**Режим scan** (без базовой точки diff):
```bash
cat "<path>"
```

Читайте каждый проверяемый файл напрямую (большие файлы — по частям); при необходимости используйте приведённые ниже команды для получения контекста.

Для получения контекста:

```bash
git --no-pager log --no-color --oneline -- "<path>"
git --no-pager blame --no-textconv -- "<path>"
git --no-pager show --no-ext-diff --no-textconv --no-color "<ref>:<path>"
```

Для больших diff добавьте `--output="<absolute-diff-file>"` в команду выбранного режима. Выберите уникальный абсолютный путь вне репозитория и создайте родительский каталог. Используйте тот же путь в вызовах инструмента чтения файлов:

```bash
git --no-pager diff --no-ext-diff --no-textconv --no-color --output="<absolute-diff-file>" <merge_base>..<to> -- "<path>"
```

После завершения Git с кодом 0 прочитайте и проверьте весь файл по частям, затем удалите его. При ошибке или тайм-ауте повторите попытку либо отметьте файл как `skipped`, указав ошибку. Если вывод неожиданно пуст, повторите preview и сопоставьте результаты.

### Шаг 4. Проверить каждый файл

Для каждого проверяемого файла:

1. Получить его diff (шаг 3).
2. Использовать подходящую группу правил (шаг 2) как контрольный список ревью.
3. Провести тщательное ревью, при необходимости исследуя контекст.

Запишите каждый элемент `(path, status)` из preview как `reviewed` или `skipped`. Укажите причину для каждого пропущенного элемента и включите в отчёт `total_files`, `reviewed_files`, `skipped_files`, `coverage_rate`.

### Шаг 5. Подготовить отчёт

Классифицируйте каждое замечание по серьёзности:

- **Critical/High** — ошибки, проблемы безопасности, риски потери данных. Всегда сообщать.
- **Medium** — проблемы производительности, недостаточная обработка ошибок. Сообщать с контекстом.
- **Low** — замечания по стилю, мелкие предложения. Незаметно отбрасывать, если они не несут явной пользы.

### Шаг 6. Записать сессию (необязательно)

Сохраните завершённое ревью как стандартную сессию OCR — её можно просматривать через `ocr session` и `ocr viewer` наравне с нативными запусками:

```bash
ocr delegate record --input <result.json> [--scan | --from <ref> [--to <ref>] | --commit <hash>] [--model <имя-модели-хоста>]
```

Запишите итоговый результат в JSON-файл вне репозитория:

```json
{
  "files": [
    {"path": "internal/app.go", "outcome": "reviewed"},
    {"path": "large.lock", "outcome": "skipped", "reason": "generated file"}
  ],
  "comments": [
    {"path": "internal/app.go", "content": "missing error handling",
     "existing_code": "f, err := os.Open(path)",
     "suggestion_code": "f, err := os.Open(path)\nif err != nil {\n    return err\n}",
     "start_line": 12, "end_line": 12, "category": "bug", "severity": "high"}
  ],
  "usage": {"prompt_tokens": 12000, "completion_tokens": 900,
            "cache_read_tokens": 4000, "cache_write_tokens": 0}
}
```

- `files` охватывает каждую запись `reviewable_files` из шага 1. `outcome` — `reviewed` или `skipped` (обязателен `reason`). Незаявленные файлы записываются как failed, и запуск завершается в состоянии `partial`.
- `comments` используют поля замечаний из шага 5 и должны ссылаться на файл, заявленный как `reviewed`.
- `existing_code` и `suggestion_code` необязательны; комментарий с предложением исправления передаёт оба поля (заменяемый фрагмент и его замену), и `ocr viewer` с расширениями IDE показывают его как применимый diff. Позицию задают `start_line`/`end_line`; `existing_code` не используется для привязки.
- `usage` необязателен и содержит собственные счётчики токенов хост-агента за весь обзор. OCR сохраняет их отдельной записью `delegate_usage`, поэтому `ocr viewer` включает их в итоги сессии и помечает как присланные хостом.
- Передавайте те же флаги режима, что и на шаге 1 (для всего репозитория — `--scan`, иначе те же флаги диапазона/коммита). OCR заново выполняет preview, чтобы зафиксировать набор selected, поэтому в режиме рабочей области записывайте сессию до применения исправлений.
- `--model` сохраняет имя модели хост-агента для происхождения и помечает присланную хостом нагрузку.

Команда выводит id сессии; `--format json` возвращает его вместе с run manifest. LLM-записи не создаются (OCR не наблюдал вызовы LLM хост-агента), а `ocr review --resume` отклоняет делегированные сессии.

## Справочник подкоманд

| Команда | Назначение |
|---------|---------|
| `ocr delegate preview [--scan]` | Выводит проверяемые файлы и метаданные режима/ссылок. |
| `ocr delegate rule <path...>` | Разрешает правила ревью и группирует их по содержимому. |
| `ocr delegate record --input <file>` | Сохраняет результат хост-агента как просматриваемую сессию. |

## Общие флаги

Во всех подкомандах `--from main` сокращает `--from main --to HEAD`. Ревью диапазона сравнивает `merge-base(from, to)..to` и не включает изменения в индексе, неиндексированные изменения и неотслеживаемые файлы. Без флагов диапазона или коммита используется режим рабочей области. Передавайте одинаковые флаги диапазона или коммита в `preview`, `rule` и `record`, чтобы использовать одну цель. Флаги диапазона и коммита взаимоисключающие. `--scan` переключает `preview` и `record` на работу со всем репозиторием и несовместим с флагами диапазона/коммита. Для `record` обязателен `--input <path>`; также принимаются `--model <name>` (происхождение модели хоста) и `--format <text|json>`.

| Флаг | Описание |
|------|-------------|
| `--from <ref>` | Исходная ссылка для режима диапазона. |
| `--to <ref>` | Целевая ссылка для режима диапазона; при указании `--from` по умолчанию используется `HEAD`. |
| `-c, --commit <hash>` | Режим одного коммита. |
| `--scan` | Весь репозиторий вместо diff (только preview/record). |
| `--repo <path>` | Корень репозитория (по умолчанию текущий рабочий каталог). |
| `--rule <path>` | Путь к пользовательскому rule.json. |
| `--exclude <patterns>` | Разделённые запятыми шаблоны исключения. |
| `-b, --background <text>` | Бизнес-контекст. |
| `-B, --background-file <path>` | Бизнес-контекст из файла Markdown (приоритет над `-b`). |
